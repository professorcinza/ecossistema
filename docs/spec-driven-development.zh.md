# 规格驱动开发 — 生态系统标准

**ponte-brasil-china · 工程宪法 · 2026年8月22日**

*架构师决定：**规格驱动开发（SDD）是整个生态系统的软件开发标准** —— 枢纽与外部项目（第六条）。先例早已存在：Our Civilization 游戏自诞生即规格驱动；本文档将此实践确立为法律。*

---

## 核心规则

**没有规格约束，不写一行代码。没有验证路径，不成一条规格。**

循环永远按此顺序：

```
规格 → 评审 → 实现 → 验证 → 标准
（草稿）（架构师）（双手）（测量/测试）（状态）
```

## 本格式

1. **按领域唯一且永久的 ID**：MOD（设备硬件）、TOS（操作系统）、APU（算力链）、SYS（治理）、EXC（开放例外）——新领域随需要产生；
2. **状态生命周期**：`草稿` → `已评审`（架构师）→ `已验证`（测量、测试或公开来源）——状态只随已记录的证据改变；
3. **显式版本化**：行为变更 = 新版本规格（v2、v3……），绝不静默修改——Git 历史即决策轨迹；
4. **一切规格居于仓库**——事实之源与实现它的代码一同版本化。

## 法律

1. **规格先于代码**：实现无对应规格之行为的合并请求一律拒绝；
2. **验证靠测量，不靠观点**："已验证"要求数字、测试或注明日期的来源；
3. **行为变了，规格先变**：规格的 diff 先于代码的 diff——同一提交或前一提交；
4. **例外是记录，不是容忍**（参见 MOD-014 与例外登记）：偏离规范者获得 ID、理由与退出计划；
5. **普遍适用**：枢纽、外部项目与任何人的贡献——规格是架构师、双手与社区之间的契约。

## 为什么

- **可追溯**：系统的每个行为都指向创造它的决策，有日期、有作者；
- **长寿命**：人来人往，规格长存——生态系统为超越双手而设计；
- **能效用于开发本身**：规格是工程的*减少浪费*——更少返工、更少孤儿代码、更少重复争论。

## 官方语言：RUST（架构师决定，2026-08-22）

**Rust 是生态系统项目的官方开发语言**——一切新代码的默认，例外须记录。

**为何——与既有规格的一致性**：

1. **无 GC 的内存安全**——根除 GrapheneOS 加固（TOS-004）所缓解的*整类*漏洞；C/C++ 严重 CVE 约 70% 属内存问题——Rust 抹去这一类别；
2. **真正的主线**——Linux 内核自 6.1 接受 Rust；新驱动以上游 Rust 编写（最相近的先例 Asahi GPU 驱动即 Rust）；上游优先（SYS-005）有现代路径；
3. **可预期的能耗**——无 GC 即无延迟尖峰、更少唤醒；零成本抽象编译紧凑——做得好即 C 级的能效；
4. **供应链**——cargo 的可复现构建与依赖审计原生实现 TOS-019。

**例外（记录而非容忍——永恒之法）**：

| 例外 | 场合 |
|---|---|
| **C** | 向 C 语言上游项目贡献（Mesa、内核核心）——说主人的语言；我方一侧用 Rust 绑定 |
| **Python** | 生态系统要求的 AI 工具链（TOS-024）——该领域的语言 |
| **Shell/其他** | 薄胶水——杀鸡用牛刀之处：记录后继续 |

## 贡献优先：分支仅作最后手段（架构师决定，2026-08-22）

对进入生态系统的每个社区项目，顺序永不变：

```
1. 立足 —— 补丁、测试、文档、逆向工程、带数据的缺陷报告：先有功，后有言
2. 贡献 —— 生态系统需要在那里存在的东西，就上到那里；
           我们的代码运行在上游，而非相反
3. 分支 —— 仅作最后手段，且须登记
```

**分支是最后手段，因为它负举证责任。仅当以下情形才成立**：

1. 上游**已死**——无在任维护者，经确认并注明日期；
2. **真诚尝试后被拒**——贡献已提交、公开讨论，拒绝基于架构且最终；
3. 分歧与宿主项目的存在**结构性不可调和**。

每个分支都作为例外登记：有 ID、注明日期的理由，以及**回归计划**——良性分支的目标，是当家园改变时回到家园。

## 逆向规格与统一战线（架构师决定，2026-08-22）

当许多项目功能与目标相同——由不同的人与团队、以不同技术维护——生态系统既不择一，也不全扶：**统一战线**。方法：

```
1. 测绘领域 —— 该领域所有项目，任何团队，任何技术
2. 逆向规格 —— 每个项目以测量出的需求为准，而非印象
3. 交集 ∪ 并集 —— 共同内核（所有人都做的=领域本质功能）
                  + 各家之长（各自独有而优秀之处）
4. 统一规格 —— 唯一规格，每条需求注明蒸馏自哪个项目
5. 单一战线 —— 该领域只此一条开发战线
```

**优先级法律**：

> **规格驱动开发 + 逆向规格 > 值得集成的现有项目**

没有项目因存在而进入；只因**覆盖从整个领域蒸馏出的规格**而进入。规格生于对众人的测绘，而非某家的偶然架构——生态系统不继承任何人的随意选择，也绝不把力气分散在孪生战线上。

**与贡献优先之桥**：统一≠重写。统一规格指出**锚**——覆盖度最高的活项目——以及生态系统在主人家中贡献补齐的缺口。仅在领域无锚时自立战线；分支仍是最后手段。

## 流水线：规格仓库 → 产品物化（架构师决定，2026-08-22）

生态系统的仓库按项目模块化组织，**仅含规格**。物化是 **CI/CD 流水线**的工作：把规格变成真实的软件产品：

```
规格仓库              流水线                                        产品
（按项目模块化，      1. 校验 —— 规格检查：格式、ID、               签名发布
 仅含规格）              状态、已声明的验证标准                    （可复现、由规格
                      2. 物化 —— 从规格生成代码（Rust，            物化、经审计）
                         规范 II），并经评审
                      3. 验证 —— 规格自身的标准作为测试运行
                         （openQA 级，TOS-013）
                      4. 产品 —— 构建、签名、发布
```

**流水线法律**：

| ID | 需求 |
|---|---|
| EST-001 | 规格是事实之源；物化代码是构建产物——派生、版本化、经评审，永非源头 |
| EST-002 | 无效规格不得入内：格式、ID、状态与验证标准自动校验（第二法自动化） |
| EST-003 | AI 辅助物化**必须经评审**——SDD 循环不变：规格→评审→实现（现为生成）→验证 |
| EST-004 | 验证即规格自测：声明的标准作为闸门运行；无闸门，不发布 |
| EST-005 | 签名可复现的发布（TOS-019）；生成代码通过依赖审计 |
| EST-006 | 语言例外（上游 C、AI Python）在自动物化之外——它们是贡献，非派生产品 |
| EST-007 | 流水线尽可能运行于生态系统自身的 APU 链上——系统物化自身 |

## 建议之筛：入口持续改善，出口规格（架构师决定，2026-08-22）

用户与利益相关者在**精益/改善文化**中提出建议——人人参与、小步持续。每条建议在成为规格特性之前，先过**技术之筛**：

```
入口（开放）          技术之筛                                  出口（三种）
┌────────────────┐   ┌──────────────────────────────┐   ┌─────────────────────┐
│ 任何人在公开     │ → │ 1. 价值 × 浪费（精益）        │ → │ 规格：作为新版本进入  │
│ 渠道建议，       │   │ 2. 与架构的一致性             │   │ 停放：带回访触发的   │
│ 附问题+提案      │   │ 3. 可验证性（第二法）         │   │ 备忘                 │
└────────────────┘   │ 4. 能耗账：耗费多于所得？      │   │ 拒绝：理由在案——     │
                      │ 5. 开放性（MOD-014）          │   │ 有档的墓园           │
                      │ 6. 简洁：最小增量             │   └─────────────────────┘
                      │ 7. 维护成本                   │
                      └──────────────────────────────┘
```

**筛法**：

| ID | 需求 |
|---|---|
| FIL-001 | 开放公开入口：任何人建议，须附观察到的问题+提案——否则是观点，不是建议 |
| FIL-002 | 先过精益测试：去除浪费或增加价值？只增成本者不通过 |
| FIL-003 | 能耗账强制：耗能多于回馈的特性必须明确自辩 |
| FIL-004 | 无验证即无规格——第二法同样适用于变更 |
| FIL-005 | 每条建议必有带理由的答复——墓园在案；环路开放，否则建议死绝 |
| FIL-006 | 通过的建议成为**版本化规格增量**（vN），绝不静默编辑 |
| FIL-007 | 系统度量：数量、通过率、决定时长——筛子也测量自己 |
| FIL-008 | 定期"改善"复查停放与拒绝——世界变了，裁决可以变 |

## 架构师之法：不对称的自上而下 ⇄ 自下而上（声明，2026-08-22）

*架构师将以不对称方式同时自上而下与自下而上工作，**只要可能**——不对称是方法，非混乱：*

- **自上而下**给*目的*：自愿景（文明、卡尔达肖夫、第二月球）降下赋予细节以意义的需求；
- **自下而上**给*摩擦*：自测量之制品（Moto G Power、RX 9070、代码中的 teia-rede）升上修正愿景的数字；
- **规格即两向相遇之地**——既非瀑布（纯自上而下溺于教条），亦非漂移（纯自下而上迷失航向）：每一时刻的主导方向是**信号最强者**——Git 历史记录每次反转；
- **先例即奠基本身**：基础 02（戴森）降临于基础 06（实测手机），二者诞下同一规格之网；宇宙与口袋同在一下午，彼此校正。
